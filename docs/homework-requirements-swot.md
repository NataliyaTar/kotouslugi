# Домашнее задание: требования на развитие портала КотУслуг

## Требование 1. Единый реестр паспортов животных

### Основной функционал

Разработать функцию ведения цифрового паспорта животного в едином реестре КотУслуг, обеспечивающую:

- регистрацию животного в реестре с привязкой к уже существующему профилю кота в системе;
- внесение и хранение данных о прививках (дата, препарат, серия, ветеринар, клиника);
- ведение родословной: указание родителей, потомков и ссылок (гиперссылок) на карточки родственных животных в реестре;
- фиксацию истории болезней, диагнозов и проведённого лечения;
- проверку при добавлении родственных связей на риск инбридинга (предупреждение при слишком близком родстве);
- отображение статуса вакцинации и полноты медицинской документации;
- возможность верификации записей ветеринарной клиникой (подтверждение прививок и диагнозов);
- сохранение всех данных паспорта в базе данных КотУслуг.

### Статистика и обратная связь

Для контроля качества питомников и прозрачности рынка реализовать:

- рейтинг заводчика / питомника на основе полноты паспортов, своевременности вакцинации и жалоб;
- возможность оставить отзыв о заводчике с привязкой к конкретному животному из реестра;
- отображение агрегированной статистики: доля животных с актуальными прививками, количество предупреждений об инбридинге;
- сохранение отзывов и рейтингов в базе данных КотУслуг.

### Интерфейс

Реализовать веб-интерфейс, позволяющий пользователю:

- просматривать и редактировать паспорт своего животного;
- переходить по ссылкам к карточкам родственников;
- видеть предупреждения о рисках инбридинга и неполной вакцинации;
- подавать заявку на верификацию записей ветклиникой.

## Требование 2. Единый реестр ветеринарных препаратов

### Основной функционал

Разработать функцию ведения реестра ветеринарных препаратов в КотУслуг, обеспечивающую:

- регистрацию производителей и импортёров ветеринарных препаратов (наименование, ИНН/рег. номер, контакты, страна);
- внесение препарата в реестр: торговое название, МНН, форма выпуска, серия, срок годности, штрихкод / QR-код;
- привязку каждой партии препарата к зарегистрированному производителю или импортёру;
- проверку подлинности препарата по коду (сканирование QR / ввод серии) с ответом «зарегистрирован / не найден / отозван»;
- ведение реестра отозванных и просроченных партий;
- фиксацию обращений о подозрении на контрафакт (пользователь сообщает о «сером» препарате);
- уведомление уполномоченных ролей (ветеринар, модератор) о подозрительных обращениях;
- сохранение всех данных реестра в базе данных КотУслуг.

### Статистика и обратная связь

Для борьбы с подпольной продажей и фальсификатами реализовать:

- дашборд с количеством проверок, выявленных контрафактов и отозванных партий;
- рейтинг доверия к производителю / импортёру на основе истории отзывов партий и жалоб;
- возможность оставить отзыв о препарате (эффективность, побочные эффекты) с привязкой к конкретной серии;
- сохранение статистики и отзывов в базе данных КотУслуг.

### Интерфейс

Реализовать веб-интерфейс, позволяющий:

- производителям / импортёрам регистрировать препараты и партии;
- ветеринарам и владельцам животных проверять подлинность препарата;
- пользователям сообщать о подозрительных препаратах;
- просматривать карточку препарата с полной информацией о производителе и статусе партии.

# SWOT-анализ

## 1. Единый реестр паспортов животных

| | |
|---|---|
| **S — Сильные стороны (Strengths)** | |
| | Централизация данных: один источник правды вместо бумажных паспортов и разрозненных записей питомников |
| | Прозрачность родословной: гиперссылки на родственников снижают риск скрытого инбридинга |
| | Контроль вакцинации: виден актуальный статус прививок до покупки животного |
| | Интеграция с существующим модулем `Cat` в КотУслуг — паспорт логично расширяет уже зарегистрированного кота |
| | Верификация клиникой повышает доверие к записям |
| **W — Слабые стороны (Weaknesses)** | |
| | Зависимость от добровольного внесения данных заводчиками — недобросовестные могут не регистрироваться |
| | Сложность проверки подлинности бумажных документов при первичной оцифровке |
| | Необходимость новых сущностей и связей в БД (родители, прививки, болезни) — выходит за рамки текущей модели `Requisition` |
| | Риск ошибок при ручном вводе родословной |
| | Нет готовой аутентификации и ролей (ветклиника, заводчик) в текущем проекте |
| **O — Возможности (Opportunities)** | |
| | Связка с услугой «Запись к ветеринару» (`vet`): клиника подтверждает прививки после приёма |
| | Предупреждения об инбридинге как уникальная ценность для ответственных заводчиков |
| | Рейтинг питомников — рыночный стимул соблюдать нормы |
| | Экспорт паспорта (PDF / QR) для выставок и продажи |
| | Расширение на другие виды животных в будущем |
| **T — Угрозы (Threats)** | |
| | Сопротивление недобросовестных заводчиков, которые выигрывают от непрозрачности |
| | Утечка персональных данных владельцев и коммерческой информации питомников |
| | Юридические вопросы: кто несёт ответственность за достоверность записей |
| | Фальсификация записей в реестре без строгой верификации |
| | Низкая вовлечённость пользователей без гос. мандата или крупных партнёров-клиник |

| | Дашборд для аналитики: регионы, бренды, динамика жалоб |

| | Регуляторные барьеры: в реальной жизни реестр ЛП ведёт государство |
| | Устаревание данных при задержке обновления партий |

## 3. SWOT проекта КотУслуг как платформы для реализации

| | |
|---|---|
| **S — Сильные стороны** | |
| | Готовый каркас: Angular 17 + Spring Boot 3, REST API, Swagger, многошаговые формы услуг |
| | Уже есть сущность `Cat` и CRUD — естественная точка входа для паспорта |
| | Паттерн `Requisition` + JSON `fields` — можно быстро прототипировать новые услуги |
| | Услуга `vet` — задел для связи с клиниками и медицинскими записями |
| | Maven multi-module, тесты, CI-friendly структура |
| **W — Слабые стороны** | |
| | H2 in-memory — данные не персистентны между перезапусками |
| | Нет аутентификации, ролей, прав доступа |
| | Бизнес-логика услуг в основном на фронте; бэкенд — тонкий слой |
| | Файлы с пометкой «Файл не трогаем» ограничивают изменения инфраструктуры |
| | Нет связей FK между котами и заявками |
| **O — Возможности** | |
| | Добавление новых услуг через `service.module.ts` + JSON-конфиг + компонент |
| | Новые JPA-сущности в `kotouslugi-core` без ломки существующего API |
| | Синергия двух реестров: паспорт ↔ препарат ↔ ветприём |
| | OpenAPI для согласования API внутри команды |
| **T — Угрозы** | |
| | Раздувание scope двух больших фич в рамках учебного спринта |
| | Конфликты при merge веток команды |
| | Дублирование логики, если не договориться о единой доменной модели |
| | Технический долг при хранении сложных данных в JSON-строке `Requisition.fields` вместо нормализованных таблиц |

## Рекомендации для команды

1. **Паспорт животного** — расширять сущность `Cat` или ввести `AnimalPassport` с One-to-One к `Cat`; родственные связи — отдельная таблица `pedigree_link`.
2. **Реестр препаратов** — новые сущности `Manufacturer`, `Drug`, `DrugBatch`; проверка по `batchCode`.
3. **Не пихать всё в `Requisition.fields`** — для постоянных данных использовать нормальные таблицы; заявки оставить для процессов (верификация, жалоба на контрафакт).
4. **Связать фичи**: прививка в паспорте → ссылка на `DrugBatch`; жалоба на контрафакт → привязка к заводчику из паспорта проданного животного.
5. **MVP**: сначала паспорт с прививками и родословной (1–2 уровня предков), затем проверка препарата по коду без полного кабинета производителя.
